# ADR-HEARTH-182: Home Assistant camera snapshot, media_player browse_media, and alarm_control_panel

**Date:** 2026-09-27
**Status:** Accepted. Implements Track A step 6 of ADR-HEARTH-174 (camera snapshot, browse_media, alarm panel only — remote access through the FCC relay is left for a later ADR); extends ADR-HEARTH-166 (driver), ADR-HEARTH-175 (shared session) and ADR-HEARTH-178 (domain mapping conventions, confirm-before-dangerous-action, headless allow-list).
**Verification:** Unit and contract tests with a mocked `fetch` and the scripted fake Home Assistant WebSocket (`src/testUtils/fakeHaServer.ts`); every new screen (camera tile, alarm code pad/confirm, media browse list) checked in the web harness (`scripts/ui-verify`, screenshots read). **No real Home Assistant instance was available this session** — see "Unverified".

## Sources fetched (2026-09-27, per this task's instruction to not rely on memory)
- developers.home-assistant.io/docs/api/rest — `GET /api/camera_proxy/<entity_id>` (Bearer header, returns the image; **does not** document `entity_picture` or an `access_token` query parameter) and `GET /api/config`.
- home-assistant.io/integrations/alarm_control_panel — services (`alarm_arm_home/away/night`, `alarm_disarm`, plus `arm_vacation`/`arm_custom_bypass`/`trigger`, not used here), states, the `code` parameter, the `changed_by` attribute.
- developers.home-assistant.io/docs/core/entity/alarm-control-panel — `code_format` (`CodeFormat` enum: none / number / text), `code_arm_required` (bool, default **true**, "whether the code is required for arm actions"), `AlarmControlPanelEntityFeature` flag names (no numeric values given), the `async_alarm_arm_*`/`async_alarm_disarm(code=None)` method signatures.
- developers.home-assistant.io/docs/core/entity/media-player — `async_browse_media(media_content_type=None, media_content_id=None) -> BrowseMedia` and the `BROWSE_MEDIA` feature flag ("Entity allows browsing media"); **does not** give `BrowseMedia`'s own field names or any feature-bit numeric values.
- Web search corroborating the `media_player/browse_media` WebSocket command shape (`entity_id` + optional `media_content_type`/`media_content_id` pair) and that browsed items are played back via `media_player.play_media` with the same two fields.

## Decisions

### 1. Camera snapshot
- No new `CapabilityId`. Fetching a snapshot is a **read**, not a Command: it never changes device state, so it does not go through `CommandEngine.execute`/`driver.executeCommand`, and per `Capability.ts`'s own rule ("do not add an id until a driver or the UI actually uses it") nothing here would ever read a `"snapshot"` capability. `DeviceCategory` gets `"camera"` instead, treated exactly like `"sensor"`/`"binary_sensor"` in `haEntityMapping.ts`'s `READ_ONLY_DOMAINS`: always offered, always an empty capability list.
- `DeviceDriver` gains an optional `fetchSnapshot(device): Promise<SnapshotImage>`, and `CommandEngine` gains a thin `fetchSnapshot(deviceId)` wrapper (mirrors `execute()`'s device/driver lookup, never throws — a `SnapshotResult` with `success`/`error` instead). `HomeAssistantDriver.fetchSnapshot` re-reads the entity fresh via REST (`client.getEntity`) every time it's called — never from the cached/polled state — and builds the image source with `haCameraSnapshot.ts`'s `cameraSnapshotSource()`:
  - If the entity's `entity_picture` attribute is present, use it directly (absolute if it already has a scheme, else resolved against the instance's `baseUrl`) — **no Authorization header**, since Home Assistant's camera integration serves that path with its own short-lived `access_token` query parameter. This specific behaviour is **not** on the fetched REST page (see Unverified).
  - Otherwise, fall back to the documented `GET /api/camera_proxy/<entity_id>` with the shared Bearer token.
- `CameraControls.tsx` (the entity screen's new tab for `category: "camera"`) calls `fetchSnapshot` exactly twice: once in a mount effect (screen open) and once per tap of its own "Refresh" button — never on an interval, never from the background 10 s poll or the WebSocket session, so a camera in the household is never silently fetched for imagery. Loaded into an RN `Image` via `source.uri`/`source.headers` (headers apply on iOS/Android; ignored on web, matching the ask).

### 2. media_player browse_media
- Two new capability ids: `"browseMedia"` (UI-only signal — gates showing the remote screen's Browse button, gated on the `BROWSE_MEDIA` feature bit) and `"playMedia"` (a real dispatched Command — HA's `media_player.play_media` service, gated on the `PLAY_MEDIA` bit). Browsing itself is **not** a Command: `CommandEngine.browseMedia(deviceId, mediaContentId?, mediaContentType?)` is a second thin read-only wrapper next to `fetchSnapshot`, refusing (gracefully, `{success:false}`) a device whose driver has no `browseMedia` or that doesn't declare the capability — this is the "browsing not supported" case the task asked for.
- `HomeAssistantDriver.browseMedia` sends `{type:"media_player/browse_media", entity_id, media_content_id?, media_content_type?}` over the existing per-instance `HaSession` (ADR-175) — reusing the device's already-open link when subscribed (the ordinary case: every device is subscribed app-wide via `stateStoreBridge.ts`), else opening a short-lived one it releases itself. If the session isn't `"live"` it throws a plain "not connected right now" rather than hanging.
- `haMediaBrowse.ts`'s `normalizeBrowseNode` maps the reply's `title`/`media_content_id`/`media_content_type`/`can_play`/`can_expand`/`thumbnail`/`children` into `MediaBrowseNode`/`MediaBrowseItem` — these field names are **not** on the fetched media-player page (see Unverified) and degrade to safe defaults (`"Untitled"`, empty strings, `false`, `[]`) rather than throwing on an unexpected shape.
- UI: `MediaBrowseModal.tsx`, a full-screen folders/tracks list with a breadcrumb trail, opened from a new "Browse" button in `UniversalTvRemote.tsx`'s existing utility row (one more `has(device, "browseMedia")`-gated entry, the same pattern as `openSourceList`). Tapping an expandable item goes a level deeper; tapping a playable one calls `commandEngine.execute({capability:"playMedia", ...})` and closes.

### 3. alarm_control_panel
- Four new capability ids: `"armHome"`/`"armAway"`/`"armNight"` (each gated on its own `AlarmControlPanelEntityFeature` bit) and `"disarm"` (always offered — an alarm you can arm but never turn off from Hearth would be a real hazard). New `DeviceCategory: "alarm"`, rendered by a new `AlarmControls.tsx` on the entity screen (alongside cover/lock/climate/fan/sensor/action).
- Live code pad: `AlarmControls` reads `values.codeFormat`/`values.codeArmRequired` (mapped in `haStateMapping.ts`'s new `alarmValues()` from the entity's own `code_format`/`code_arm_required` attributes, `code_arm_required` defaulting **true** per the fetched entity docs) and decides per press whether to ask for a code first: never when the panel has no `code_format` at all; for **disarm**, always (that is what actually secures the panel); for an **arm** action, only when `code_arm_required` was not explicitly turned off. The code lives only in the component's own React state, is passed once as `{code}` on the Command's `args`, and is never persisted or logged (checked directly by the existing "the token never appears in any log line" style test, extended for this driver's other secrets).
- Confirm step: `commandConfirmation.ts`'s `needsConfirmation`/`confirmationFor` now also cover the four alarm capabilities (a new `ALARM_CAPABILITIES` set alongside the existing lock/cover one), with alarm-specific wording ("This changes your home's security system") instead of the lock/cover set's "who can get into the house." The code pad and the confirm card are two separate steps, in that order — entering a code is not itself the confirmation.
- Clear visual distinction: the status line colors `triggered` with `theme.statusError` and any `armed_*` state with `theme.statusOn`; every other state (disarmed, pending, arming, disarming) reads in the plain default text color.
- `commandToServiceCall`'s alarm branch sends `code` only when one was actually typed, matching HA's optional parameter — the code is never defaulted or synthesized.
- Camera **and** alarm are excluded from Activities/the scheduler, the same way ADR-178's follow-up refused `unlock`: `activityRunner.ts`'s `NEVER_IN_ACTIVITY_CAPABILITIES` now also lists `armHome`/`armAway`/`armNight`/`disarm`. Camera needs no entry there at all — it has no capability id, so it structurally cannot appear as an `ActivityStep` in the first place (defense in depth beats a symbolic entry for a capability that was deliberately never created). Separately, `headlessSupport.ts`'s `HEADLESS_DRIVER_IDS` already excludes `home-assistant` entirely, so nothing from this ADR could reach the Family Command Center's scheduled runner even before this change.

## Questions and answers (ADR-GLOBAL-002)
- *Does a camera need a `"snapshot"` capability id?* No — see Decision 1. Logged here rather than asked live: the task's own instruction ("add only if actually used, per Capability.ts's own rule") already supplied the decision rule; this is its straightforward application, not a genuinely ambiguous fork.
- *Is `code_arm_required` checked for disarm too?* No — HA's own docs say it governs arm actions; disarm always takes the code when the panel has a `code_format`, which is the behavior that actually matters for security.
- *Cameras default ticked or unticked on the sync screen?* Ticked (unlike sensors) — a home typically has a handful of cameras, not hundreds, so the "opt in because it's noisy" reasoning `haImportCandidates.ts` uses for sensors doesn't apply.
- *Should `playMedia`/`browseMedia` also be blocked from Activities?* No — the task scoped the "too dangerous unattended" concern to camera and alarm specifically; playing a saved playlist from an Activity is not a safety-relevant action the way arming/disarming or a live camera feed inside an unattended automation would be.

## Unverified
- **No real Home Assistant was contacted.** In the same spirit as ADR-175/178's own "Unverified" sections:
  - The `entity_picture` short-lived `access_token` query-parameter behavior for camera entities is not on the fetched REST docs page — it comes from Home Assistant's frontend/camera-integration behavior as remembered, not confirmed against a live server.
  - `AlarmControlPanelEntityFeature` bit values (`ARM_HOME=1, ARM_AWAY=2, ARM_NIGHT=4`) and `MediaPlayerEntityFeature.BROWSE_MEDIA=131072`/`PLAY_MEDIA=512` are from Home Assistant's source as remembered — the fetched developer pages name the flags but never give their numeric values.
  - `BrowseMedia`'s own reply field names (`title`, `media_content_id`, `media_content_type`, `can_play`, `can_expand`, `thumbnail`, `children`) are not on the fetched media-player page either — from the frontend's well-known consumption of it, same Unverified status.
  - The alarm code pad, the camera snapshot tile and the media browse list were only exercised in the web harness (`scripts/ui-verify`) with demo/fake data — a live `entity_picture` token's actual short lifetime, a real panel's `code_format`/`code_arm_required` combination, and a real integration's `browse_media` reply shape are all unconfirmed against a live server.
  - iOS/Android rendering of `Image`'s `source.headers` (used for the camera proxy fallback) is unchecked — the web harness cannot exercise it at all, since a browser `<img>` tag can't carry custom request headers; the `entity_picture` path (no headers) is what the harness's own demo scenario actually renders.
